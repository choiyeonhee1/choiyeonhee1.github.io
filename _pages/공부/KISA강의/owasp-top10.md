# 웹 취약점 이해 — OWASP Top 10
      
## IDOR (Insecure Direct Object References)
- 접근 제어(Access Control)와 관련된 취약점임
- 사용자 입력값이 객체(Object)에 직접 매핑되어 접근될 때, 공격자가 자신의 권한을 넘어서는 동작을 수행할 수 있는 경우를 말함
- 예: 계정 설정 페이지 URL에 사용자 ID가 그대로 들어가 있는 경우 → ID 값만 바꾸면 다른 사용자의 계정 설정 페이지에 접근 가능함
- 수평적 권한 상승(Horizontal Privilege Escalation): 공격자가 동일한 권한 수준을 가진 다른 사용자의 데이터에 접근/조작하는 상황
- 수직적 권한  상승(Vertical Privilege Escalation): 애플리케이션 구성/정책에 따라 더 높은 권한을 가진 사용자의 정보까지 접근/조작하게 되는 상황
- 예시: `abc.com/user-info?uid=1001` → `uid=1003`으로 변경하면 다른 사용자 정보 조회 가능
  - 파라미터가 숫자(Sequential ID)인 경우, 값을 단순 증감시키는 것만으로도 자주 발견됨
- 숫자 증감 외에 다양한 방식으로도 트리거될 수 있음
  - 문자열(사용자 이름 등)이나 파일 이름 변경
  - HTTP 메서드(Method) 변경
  - Content-Type 변경
  - 기대하는 값의 타입 변경 (예: 단일 숫자 대신 리스트 형태로 전달)

## XSS (Cross Site Scripting)
- 공격자가 HTML/JavaScript 등 스크립트를 웹페이지에 삽입하고, 다른 사용자가 이를 실행하게 만들어 정보를 탈취하거나 행동을 조작하는 취약점임
- OWASP Top 10에 거의 매번 포함될 만큼 널리 알려진 취약점이고, 오래됐음에도 여전히 많이 발생함
- 기본 3가지 유형
  - Reflected XSS: 사용자가 입력한 데이터를 서버가 바로 반영해서 스크립트가 실행되는 형태
  - Stored XSS: 사용자가 입력한 데이터가 서버에 저장됐다가, 다른 사용자가 해당 데이터를 요청할 때 스크립트가 실행되는 형태
  - DOM based XSS: 서버가 아닌 사용자 브라우저 내에서 스크립트가 실행되는 형태
- 그 외 특수 상황에서 발생하는 유형: Blind XSS, Universal XSS, Server-side XSS, Mutated XSS 등

### Reflected XSS 공격 흐름
1. 공격자가 취약한 사이트를 발견하고, 악성 스크립트가 포함된 URL을 생성함
2. 이메일/메시지 등으로 사용자에게 URL을 전달함 (스팸 형태가 많음)
3. 사용자가 링크를 클릭 → 브라우저가 취약한 웹 서버로 요청을 보냄
4. 서버가 요청을 처리하고, 악성 스크립트가 포함된 응답을 반환함
5. 사용자 브라우저에서 스크립트가 실행됨 → 민감 정보가 공격자에게 전달됨

- 취약 코드 패턴 예: URL 파라미터 값이 `<input>` 태그의 value 속성에 그대로 삽입되는 경우
  - 공격자가 따옴표(`"`)나 `>`로 태그를 닫고 뒤에 스크립트를 이어 붙이면, 렌더링 시 스크립트가 그대로 실행됨
- 모의해킹(Penetration Testing) 상황에서는 `alert()` 함수 실행만으로도 취약점 존재를 확인할 수 있지만, 실제 버그헌팅에서는 이 취약점이 실제로 어떻게 악용될 수 있는지까지 설명할 수 있어야 함

### Stored XSS 공격 흐름
1. 공격자가 취약한 사이트를 찾아 게시판 등에 악성 스크립트가 포함된 게시글을 작성함
2. 다른 사용자가 게시글을 읽으려 하면 서버가 악성 스크립트가 포함된 게시글을 전달함
3. 사용자 브라우저가 게시글을 렌더링하는 과정에서 스크립트가 실행됨 → 민감 정보 탈취
- 게시판, 사용자 프로필처럼 서버에 데이터가 저장되는 곳에서 주로 발견됨

### DOM based XSS 공격 흐름
1. 공격자가 취약한 페이지를 찾아, 악성 스크립트가 실행되도록 조작된 URL을 생성함
2. URL을 사용자에게 전달하고 사용자가 클릭함
3. 서버는 해당 URL에 대응하는 HTML 문서를 그대로(변조 없이) 반환함
4. 브라우저가 HTML을 해석하고 스크립트를 실행하는 과정에서 공격자가 조작한 스크립트도 함께 실행됨 → 민감 정보 탈취
- Reflected XSS와 비슷해 보이지만 핵심 차이는, DOM 기반 공격은 서버 로그(Server Log)에 흔적이 남지 않는다는 점임 (모든 동작이 브라우저 내에서만 발생함)
- 관련 개념
  - `location.hash`: URL의 `#`(프래그먼트) 뒤에 오는 값
  - `location.assign()`: 입력받은 URL로 페이지를 이동시키는 JavaScript 함수
  - hash 값에 `javascript:alert(1)` 같은 문자열이 들어가면 JS 프로토콜에 따라 브라우저에서 코드로 해석/실행됨
- 서버로의 직접적인 요청이 없기 때문에 서버 측에서 이 공격을 탐지하기 매우 어려움

## CSRF (Cross Site Request Forgery)
- 로그인 시 서버가 부여하는 Session ID는 쿠키에 저장되고, 이후 요청마다 사용자 신원 확인에 사용됨
- 외부 사이트가 이 쿠키를 이용해 사용자 대신 서버에 요청을 보내게 만드는 것이 CSRF임
- 정의: 사용자의 인증 정보를 이용해, 사용자 의지와 무관하게 공격자가 의도한 요청을 처리시키는 공격
- 시나리오 예: 은행 사이트에 로그인한 상태에서 공격자가 보낸 악성 URL을 클릭 → 계좌 이체가 실행됨
  - 현재는 2차 본인 인증으로 방지되지만, 과거엔 실제로 가능했던 공격 형태임
- 사용자의 클릭 없이도 자동으로 요청이 전송되도록 만드는 페이로드(Payload)도 존재함 → 사용자가 전혀 인지하지 못한 채 공격당할 수 있음
- 요청 형식에 따라 페이로드 형태도 달라짐
  - 파일 업로드가 필요하면 Multipart/form-data 형식
  - 서버가 JSON Content-Type을 예상하면 그에 맞는 형식으로 전송

## SQL Injection
- 로그인, 회원가입, 검색 등 사용자 입력이 필요한 기능은 대부분 데이터베이스(Database)에 SQL로 질의함
- 사용자 입력값에 `'`, `"`, `\` 같은 특수문자가 그대로 SQL 구문에 섞여 들어가면 SQL Injection이 발생함
- 정의: 공격자가 SQL 구문의 원래 의미를 바꿔서 예상치 못한 동작이나 정보 유출을 일으키는 공격
- 예: 아이디 값에 `admin'--`처럼 입력 → 뒤에 오는 비밀번호 검증 구문이 주석 처리(`--`)되어 아이디만으로 로그인이 통과됨

### 6가지 유형
1. Boolean-based Blind SQLi: 참/거짓 조건 쿼리로 반응 차이를 이용함 (예: `1=1`은 참, `1=0`은 거짓) → 특정 정보의 첫 글자를 조건에 하나씩 넣어보며 값을 추출
2. Error-based SQLi: 일부러 잘못된 쿼리를 넣어 에러 메시지에 정보가 노출되게 함
3. UNION-based SQLi: `UNION`으로 두 쿼리를 합쳐서 실행함 (컬럼 개수를 맞추기 위해 `NULL`을 채워 넣기도 함)
4. Stacked Query SQLi: 쿼리를 끊고 추가 쿼리를 삽입해서 실행함
5. Time-based Blind SQLi: `SLEEP()`, `WAITFOR` 같은 함수로 조건에 따라 응답 시간을 다르게 만들어 정보를 추출함
6. Inline Query SQLi: `SELECT` 쿼리 안에 동일한 `SELECT` 서브쿼리(Subquery)를 삽입해서 실행함

### 탐지 팁
- SQL Injection이 발생하기 쉬운 파라미터를 먼저 주의 깊게 살펴봄
- 값에 `-1`을 넣어봐서 결과값이 1 줄어든 값으로 추론되면, 해당 값이 정수형으로 인식돼 쿼리 연산에 사용됐다는 걸 알 수 있음
- 정해진 방법론보다는 상황에 맞게 여러 시도를 해보는 경우가 많음 → 다른 버그바운티 사례를 많이 보면서 패턴을 익혀두는 게 도움이 됨

## File Inclusion (LFI/RFI)
- 디렉토리 트래버설(Directory Traversal)과 유사하지만 다른 취약점임
  - 디렉토리 트래버설: 파일을 "읽는" 기능만 대상
  - File Inclusion: 파일을 동적으로 "포함(Include)"하는 기능을 악용 → 시스템 파일을 읽거나, 공격자가 준비한 코드를 포함시켜 실행

### LFI (Local File Inclusion)
- 로컬에 있는 파일을 읽는 공격임
- 예: `file` GET 파라미터에 `../../../etc/passwd` 같은 경로를 넣어 시스템 파일을 탈취
- 파일 업로드 기능이 있다면, 확장자를 `.txt`로 업로드해도 `include()` 함수가 내용을 PHP 코드로 해석/실행할 수 있음 → 원격 코드 실행(RCE)까지 이어질 수 있음 (취약점을 엮어서 더 큰 공격으로 발전시키는 것을 취약점 체이닝, Vulnerability Chaining이라고 함)
- LFI를 로그(Log) 파일과 함께 쓰는 공격도 가능함 (파일 업로드 기능이 없을 때 특히 유용)
  - 예: `curl`의 User-Agent 헤더에 PHP 코드를 삽입하면 아파치(Apache) `access.log`에 그대로 기록됨 → LFI로 해당 로그 파일을 불러오면 삽입된 코드가 실행됨
  - `access.log` 외에 `ssh` 로그 등 다른 로그 파일도 비슷한 방식(로그인 시도 시 사용자 이름에 코드 삽입)으로 악용 가능함

### RFI (Remote File Inclusion)
- 공격자가 원격으로 제어하는 파일을 웹 서버가 포함(include)하게 만드는 공격임
- 예: 공격자가 자신의 서버에 셸 코드(Shell Code)가 담긴 파일(`shell.txt`)을 올려두고, 취약한 서버가 이 파일을 include 하도록 만듦 → 서버에서 공격자가 의도한 명령이 실행됨
- LFI와 원리는 비슷하지만, 포함되는 파일이 로컬이 아닌 원격 서버에서 호스팅된다는 점이 다름

## SSRF (Server-Side Request Forgery)
- 공격자가 서버로 하여금 의도한 외부(또는 내부) 요청을 보내게 만드는 공격임
- 예: URL 파라미터에 `127.0.0.1`을 넣으면 서버가 자기 자신에게 요청을 보내고, 그 결과가 공격자에게 전달될 수 있음
- URL 파라미터에 다른 서버 주소를 넣으면 서버가 그 서버로 대신 요청을 보내게 만들 수도 있음
- HTTP 요청에만 국한되지 않음: DB 연결 요청, SMB, SSH Connection, curl 명령어 파라미터 등 다양한 환경에서 발생 가능함
- 최신 웹 개발 환경에서는 직접 HTTP 요청 코드를 짜기보다 특정 라이브러리나 외부 프로그램(curl, wget 등)을 이용하는 경우가 많고, 여기서도 SSRF가 발생할 수 있음
- 주 활용: 포트 스캐닝(Port Scanning), 내부망(Internal Network) 서비스 접근
- 다른 취약점과 연계되는 경우도 많음
  - 예: AWS 메타데이터(Metadata) 엔드포인트에 접근해 AWS Credential(Access Key/Secret Key)을 탈취 → AWS 버킷(Bucket) 접근/파일 다운로드까지 이어질 수 있음
  - XSS와 연계해서 `file://` 프로토콜로 내부 파일을 탈취하는 사례도 있음
