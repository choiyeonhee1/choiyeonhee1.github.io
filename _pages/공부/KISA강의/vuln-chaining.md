# 시나리오 개발 & 취약점 체이닝

## 시나리오(스토리텔링)의 중요성
- 버그헌팅에서 취약점을 제보하는 과정은 스토리텔링(Storytelling)에 가까움
- 단순히 문제가 존재한다는 것만 보여주는 게 아니라, 그 문제로 인해 발생할 수 있는 실질적인 피해 시나리오를 제시하는 게 중요함
- 예: XSS(Cross Site Scripting) 취약점을 발견했더라도, HttpOnly 옵션이 설정돼 있으면 스크립트로 세션(Session)을 탈취할 수 없음
  - 이 경우 단순히 스크립트가 실행된다는 것만 보여주기보다, 실제로 어떤 피해를 줄 수 있는지를 보여줘야 함
  - 예: 개발용으로만 쓰려던 세션 정보 노출 테스트 페이지가 운영 환경에도 노출돼 있다면, XSS로 그 페이지를 호출해서 응답값의 세션 정보를 추출해 공격자 서버로 전송하는 시나리오를 제시할 수 있음
  - 세션 탈취 시나리오가 불가능하다면 오픈 리다이렉트(Open Redirect) 악용, 브라우저 자원 과도 소비, 브라우저 제로데이(0-day) 취약점을 이용한 시스템 접근 등 다른 시나리오를 고려해볼 수 있음
- 핵심은 "문제가 있다"를 보여주는 게 아니라 "이 문제로 어떤 피해가 가능한가"를 보여주는 것임 

## 예시: XSS + 세션 정보 노출 페이지 체이닝
- 특정 페이지에서 스크립트를 실행할 수 있는 XSS를 발견했지만, HttpOnly 옵션 때문에 쿠키(세션 값)를 직접 탈취하지는 못하는 상황을 가정
- 이 상태로 제보하면 피싱 페이지로 유도하거나 특정 스크립트를 실행시키는 정도의 제한적인 시나리오밖에 설명할 수 없음
- 그런데 별도로 세션 정보가 노출되는 페이지를 발견했다면, 이 둘을 연결할 수 있음
  - `document.evaluate()` 함수 등으로 해당 페이지의 세션 정보 텍스트를 가져와서 GET 방식으로 공격자 서버에 전송하는 스크립트를 작성
  - 세션 탈취가 불가능했던 XSS + 세션 정보가 노출된 페이지 → 최종적으로 세션 탈취가 가능한 XSS 취약점이 됨
- 이렇게 여러 취약점을 연결하는 형태를 취약점 체이닝(Vulnerability Chaining)이라고 함
- 하나의 취약점만 발견하는 것보다, 여러 취약점을 체이닝해서 더 큰 파급력을 만드는 것이 중요함 (XSS뿐 아니라 다른 취약점에도 동일하게 적용 가능)
- 시스템을 충분히 이해하고, "내가 공격자라면 이 서비스를 어떻게 공격할까?"라는 관점을 가지고 접근하는 게 도움이 됨

## 셀프 XSS (Self-XSS)
- 사용자가 자기 자신에게만 스크립트 공격을 가하게 되는 형태의 XSS임
- 공격자가 사이트에 직접 악성 스크립트를 심는 게 아니라, 피해자 스스로 본인에게 피해를 입히는 특징이 있음
- 예: 본인만 볼 수 있고 본인만 쓸 수 있는 블로그 글에 XSS가 있어도, 본인이 본인에게 피해를 주는 것이라 실질적인 피해는 거의 없음


## 취약점 체이닝 (Vulnerability Chaining) 개념 정리
- 2개 이상의 취약점을 연결해서, 개별적으로는 중요하지 않은 보안 이슈들을 결합해 강력한 공격 시나리오를 만드는 방법임
- 하나의 취약점만으로는 제한적인 권한만 얻는 경우가 많지만, 여러 취약점을 결합하면 효과가 기하급수적으로 커질 수 있음

### 예시: 임의 파일 쓰기(Arbitrary File Write) + LFI 체이닝
- 과거 오픈소스 코드를 바탕으로 만든 참고용 시나리오임
- 임의 파일 작성 취약점으로 원하는 PHP 코드를 파일에 작성할 수 있었지만, 해당 파일에 접근 권한 제한이 있어 직접 접근은 불가능했음
- LFI(Local File Inclusion) 취약점으로 우회함
  - 상위 경로 이동(`../`)에 대한 필터링은 있었지만, 하위 디렉토리로 내려가는 슬래시(`/`)에 대한 필터링은 없었음
  - 이 점을 이용해 문서 루트(Document Root) 하위의 PHP 파일을 불러와 원하는 코드를 실행하는 시나리오를 완성함
- 이렇게 독립적으로는 큰 위협이 아닌 취약점들도 체이닝하면 큰 피해로 이어질 수 있음 (예: 셀프 XSS + CSRF 조합도 대표적인 예)

## 실제 사례: Uber (2016) 셀프 XSS + 응답 헤더 조작 체이닝
- 처음에는 `m.uber.com`의 프로필 리뷰(Review) 항목에서 본인만 확인 가능한 셀프 XSS를 발견함 → 이 자체로는 위협이 크지 않음
- 이후 파라미터 조작을 통해 응답 헤더(Response Header)의 Set-Cookie 값을 조작할 수 있는 취약점을 추가로 발견함
  - 이것만으로도 단독으로는 큰 영향력은 없었음
- 두 취약점을 연계한 공격 시나리오
  1. 공격자가 헤더 조작 취약점이 있는 URL을 피해자에게 전달함
  2. 피해자가 해당 URL에 접근하면 Set-Cookie 헤더를 통해 공격자의 세션 ID를 받게 되고, 그 세션으로 공격자 계정에 로그인된 상태가 됨
  3. 이때 공격자가 미리 심어둔 셀프 XSS 페이로드가 실행됨
  4. 이 페이로드가 피해자 브라우저 쿠키에 저장된 OAuth 토큰을 탈취해서 공격자에게 전송함
  5. 결과적으로 공격자가 피해자 계정을 완전히 탈취하게 됨
- 각각은 큰 문제가 아니었던 두 취약점을 연결해서 심각한 계정 탈취(Account Takeover) 취약점으로 발전시킨 사례임
