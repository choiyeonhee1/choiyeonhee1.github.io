# 클라이언트-서버 통신 & HTTP 요청/응답 

## 클라이언트-서버 통신 구조
- 웹뿐 아니라 모바일 앱, 게임, IoT(자동차 등) 다양한 분야에서 쓰이는 구조임
- 핵심은 클라이언트(Client)와 서버(Server)의 역할이 분리되어 있다는 것임
- 탈중앙화(Decentralized), 디파이(DeFi) 같은 개념은 중앙 집중형 서버 없이 클라이언트들끼리 서로 서버 역할을 나눠 맡는 방식임

## 요청 처리 흐름
- 사용자가 브라우저에서 페이지 요청 → 회사 서버로 전달됨
- 서버 위치
  - 온프레미스(On-premise): 회사가 직접 서버를 구축/운영
  - 오프프레미스(Off-premise): IDC 센터나 클라우드(Cloud)를 이용
- 요청을 가장 먼저 받는 곳은 웹 서버(Web Server, 예: Nginx)
  - 정적 콘텐츠(Static Content, 이미지/CSS/JS 등) 요청 → 바로 찾아서 반환
  - 동적 콘텐츠(Dynamic Content) 요청 → 웹 애플리케이션 서버(WAS, Web Application Server)로 전달
- WAS(예: Tomcat, Django, Node.js 등)가 해당 언어로 작성된 애플리케이션을 실행함
  - 필요하면 데이터베이스(Database)에 접근해 데이터 조회/저장
  - 필요하면 파일 서버(File Server)에 접근해 파일 읽기/저장
- 처리 결과는 다시 웹 서버를 거쳐 클라이언트에게 반환됨
- 각 요소의 역할/순서는 아키텍처(Architecture)에 따라 달라질 수 있음

## GET 요청
- 서버로부터 정보를 요청하는 가장 일반적인 방식임
- 요청 데이터를 URL에 쿼리스트링(Query String) 형태로 포함함 (예: `?page=1&sort=asc`)
- URL 길이 제한(보통 2000~3000자) 때문에 전송 가능한 데이터 양이 제한됨
- 특징
  - 브라우저가 결과를 자동으로 캐싱(Caching)함
  - 브라우저 히스토리(History)에 기록됨
  - 안전한 메서드(Safe Method): 서버 상태를 변경하지 않음
  - 멱등성(Idempotent) 있음: 여러 번 요청해도 결과가 항상 동일함
  - 북마크(Bookmark) 가능함
- 민감한 정보 전달이나 서버 상태 변경이 필요한 경우에는 POST, PUT, DELETE 등을 사용하는 게 적절함

## HTTP 응답 구조
- 상태 코드(Status Code): 응답 맨 앞에 오는 3자리 숫자, 요청 처리 결과를 나타냄 (예: 200은 성공, 404는 리소스를 찾을 수 없음)
- 헤더(Header): 응답에 대한 메타데이터(Metadata). 콘텐츠 타입, 캐싱 정책, 쿠키 등 정보 포함
- 바디(Body): 실제 데이터. 요청 종류에 따라 HTML 코드일 수도, JSON 데이터일 수도 있음

## POST 요청
- 클라이언트가 서버로 데이터를 전송할 때 사용, 주로 리소스 생성이나 상태 업데이트에 쓰임
- 전송 데이터는 요청 바디(Request Body)에 포함됨 (형식은 JSON, XML 등 다양함)
- GET과 달리 전송 데이터 크기 제한이 없음
- 브라우저 히스토리에 기록되지 않고, 자동 캐싱도 되지 않음
- 이 특성 때문에 새로고침/뒤로가기 시 "다시 제출하시겠습니까" 같은 경고가 뜸
- 멱등성이 없음: 같은 요청을 여러 번 보내면 서버 상태가 그만큼 바뀜 (예: 같은 글쓰기 요청 반복 시 게시글이 중복 생성됨)

## 버그헌팅 관점에서 본 HTTP 메서드
- GET: 쿼리 파라미터로 정보 요청함 → 입력값에 따른 서버 반응(민감정보 노출 등) 확인
- POST: 요청 바디를 변조해서 서버 반응 확인 → 입력 검증(Validation) 부족하면 데이터 오염 가능
- PUT: 기존 리소스 업데이트에 사용됨 → 권한 검증 없이 다른 사용자 데이터를 수정할 수 있는지 확인
- DELETE: 리소스 삭제에 사용됨 → 권한 없는 삭제 요청이 가능한지 확인
- OPTIONS: 서버가 지원하는 HTTP 메서드 목록을 반환함 → 허용되면 안 되는 메서드가 열려있는지 확인에 활용
- TRACE: 요청 메시지의 루프백(Loopback) 테스트 → 요청이 서버까지 전달되는 과정에서 어떻게 변경되는지 확인 가능

## 쿠키(Cookie)와 HttpOnly
- 로그인 성공 시 서버가 Set-Cookie 헤더로 세션 ID(Session ID)나 토큰(Token) 등을 담아 응답함
- 브라우저는 이 쿠키를 저장하고, 이후 같은 사이트로 요청을 보낼 때마다 자동으로 포함시킴
- HttpOnly 옵션: 자바스크립트(JavaScript)로 쿠키에 접근하지 못하게 막는 옵션임
  - XSS(Cross Site Scripting) 공격으로 쿠키를 탈취하는 것을 방지하는 목적임
  - 설정된 쿠키는 HTTP/HTTPS 요청을 통해서만 전송됨
- 버그헌팅 시 HttpOnly 옵션이 제대로 설정돼 있는지, 이를 우회할 방법이 있는지 확인하는 게 중요함

## User-Agent 헤더
- 클라이언트의 종류, 버전 정보, 운영체제(OS) 등의 정보를 서버에 전달하는 요청 헤더(Request Header)임
- 서버는 이 정보를 바탕으로 모바일/데스크탑 등 환경에 맞는 최적화된 페이지를 제공할 수 있음
- 브라우저 기본 속성이지만 임의로 변경 가능함
- 버그헌팅 관점
  - User-Agent를 조작해서 서버가 예외 상황을 어떻게 처리하는지 확인 가능
  - 특정 브라우저/운영체제에서만 정상 동작하도록 설계된 경우, 다른 User-Agent로 요청했을 때의 반응 확인
  - 특정 User-Agent로만 접근 가능한 서비스의 경우, 이를 위조해 클라이언트 환경을 속이고 접근을 시도할 수 있음
